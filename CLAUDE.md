# Working agreement

This is an MVP. The rules below exist so scope stays fixed. Read them before writing code.

## Scope rules (highest priority)

1. **The Notion database ["Vazifalar"](https://app.notion.com/p/55b59dbe8eb4414490bd2baa79cc6540) is the source of truth for what to build.** Work only on rows whose `Doira` is `MVP` and whose `Holat` is not `Tayyor`, in `Tartib` order. The plan is written in Uzbek: `Doira` = scope (`MVP` / `Keyin` / `Bekor`), `Holat` = status (`Rejada` / `Jarayonda` / `Bloklangan` / `Tayyor`).
2. **No feature that is not in the roadmap.** If you think of one (or the user asks for something not listed), do not build it. Add it to the Notion plan with `Doira` = `Keyin`, say so in one line, and ask whether to move it to `MVP`.
3. **Finish before starting.** Do not begin a new row while another is `Jarayonda`.
4. **Bug fixes, tests, and refactors needed to finish an MVP row are in scope.** Cleanup that serves no MVP row is not.
5. Do not propose new features unprompted while an MVP row is open. Recommendations are welcome only when the user asks "what's next" or asks for research.

## Log every change

After each completed change, before reporting it done:

- Add an entry to `docs/CHANGELOG.md` (newest first): what changed, files touched, how it was verified.
- Set the row's `Holat` to `Tayyor` in Notion, and regenerate the `docs/ROADMAP.md` snapshot.
- If it changes how the system works, update the "Architecture rules" section below.

`docs/ROADMAP.md` is a read-only snapshot of that database so the plan stays readable without Notion. When Notion is unreachable, work from the snapshot and reconcile once it is back. Related Notion pages: the [plan overview](https://app.notion.com/p/3e039db48ef981bb9c26e3b652eeebaa), the [Modullar](https://app.notion.com/p/cea1e64dba26420d8a3d5088f9272201) database (one page per module, with its tasks), and the [competitor notes](https://app.notion.com/p/3e139db48ef981f2adb7f6d10f919ed5).

Starting a session on a new machine or after a break: read `docs/HANDOFF.md` first — current state, open issues, and setup.

## Commands

```
npm run dev          # vite dev server (http://localhost:3000 by default; pass --port to change)
npm run check        # service, database and feature tests (plain node scripts, no framework)
npx tsc --noEmit     # typecheck
npm run eval         # generate eval/briefs.json through the real pipeline -> eval/out/<label>/ (costs LLM tokens)
                     #   flags: --only id,id  --limit n  --concurrency n  --label name  --no-shot
```

A change is not done until `npm run check` and `npx tsc --noEmit` are clean. UI changes must also be exercised in a real browser (golden path plus one edge case) — type checks do not prove a feature works.

A change to generation (prompts, planner, normalizer, linter, shell) is judged on the eval set, not on one hand-picked prompt: run `npm run eval -- --label <what-changed>` and read `compare.html` and the metrics delta against the previous run. Use `--only` while iterating; a full run is 28 briefs.

## Model policy

Generation runs on DeepSeek V4 Flash (`deepseek-flash`), and nothing else — not `deepseek-v4-pro`. The id is pinned in `LlmService`, because `deepseek-flash` thinks by default and an alias can be re-pointed. (The old `deepseek-chat` id is an alias of exactly this configuration.) **Thinking is decided per call site, not once**: off for the six or seven screen calls, because reasoning tokens bill as output and output is the expensive half of an app (~47k of ~86k tokens; one plan measured 8 924 tokens / 89s with it on against 2 075 / 17s with it off), and off for the planner too, which an A/B settled rather than taste: on the same brief it produced a smaller plan for five times the output tokens and five times the wait (6 screens / 8.8s / 2 283 tokens against 5 / 43.6s / 10 658), and at the old 4 000-token cap the reasoning ate the JSON and two briefs drew nothing at all. `LLM_PLAN_THINKING=1` keeps the question askable — with it the planner's cap rises to 12 000, because reasoning spends the same budget as the answer. The price table (`PRICES`, by model, with `isPeak`) holds each provider's real list price and knows that DeepSeek's peak costs double, because the daily budget guard and credit prices spend against it; `costOf` refuses a model with no row instead of calling it free, and the process refuses to boot on a `DEEPSEEK_MODEL` it cannot price. Push correctness into deterministic code instead of asking a model to hold a contract — see the next section.

For local testing only, `LLM_PROVIDER=claude-cli` routes generation through the developer's own Claude Code login (`claude -p`) so trying things costs no DeepSeek balance. It runs on Haiku 4.5 by default — local testing is about seeing a change land, not about quality — and `CLAUDE_CLI_MODEL` overrides that when a run needs the bigger model. Thinking is off there as it is on DeepSeek (`MAX_THINKING_TOKENS=0` in the child's environment): with it on, one plan cost 8 900 output tokens and 89s instead of 2 100 and 17s, which reads as a hang. It refuses to run with `NODE_ENV=production`. Evals may run on it (`run.json` records the provider; a run is only compared with runs on the same provider) — such a result says how a code change moves quality, and key results are re-checked on DeepSeek before launch.

## Architecture rules

- **Consistency across screens is enforced in code after generation, never by prompt wording.** Parallel LLM calls are independent samples. Anything that must match across screens belongs in `ShellService`, `lib/screen-normalizer.ts`, or `lib/design-lint.ts`. Prompt text should only tell the model *not* to draw things the code injects.
- **The house style goes in as markup, built in code.** Every screen of an app (planned, added or redrawn) gets the same component sheet from `ComponentSheetService` — kit snippets filled with the plan's entities — under `# HOUSE STYLE` in its brief. There is no anchor-first round trip and no CSS digest of another screen; all planned screens draw in parallel.
- **Layers:** `app/Models` (data access), `app/Services` (logic), `app/Http/Controllers` (request handling), `routes/` (TanStack file routes), `server/fns.ts` (route-to-controller binding). Migrations are numbered files in `database/migrations`, registered in `database/migrate.ts`.
- **The plan is a contract checked in code, not a suggestion.** `parsePlan` closes the vocabulary (`ARCHETYPES`, icon names, screen types), enforces one root screen per tab, prunes tabs no screen opens, keeps only links to real screens, cleans the data model, and reports requested screens the plan dropped; `planScreens` spends one repair call on those. The app's data model (`entities`) is stored in `projects.plan` and put into every screen's brief by `dataBlock` — a screen never invents its own dishes, transactions or tasks.
- **Structure comes from blueprints, not from the model's memory.** `blueprints/<archetype>.json` holds one pattern per planner archetype (sections, where the primary action lives, what to avoid); `screenSpec` puts the planned screen's pattern into its spec via `BlueprintService`. A new archetype needs a blueprint (`services.check.ts` enforces one per archetype), and a change to a blueprint is a generation change — judge it on the eval (`plan.bottomBarShare` measures adherence). Each blueprint has 2–3 layout variants; `BlueprintService.variant` picks one per app (seeded by the app name), so one app is coherent and different apps differ (`sameness.sameKindMean`).
- **The app type is decided in code, before planning.** `AppPatternService.classify` matches the brief to one of `app-patterns/*.json` by keywords (en/uz/ru) and only that pattern goes into the planner's user message, worded as subordinate to the brief: a pattern may fill open slots but never displace a requested screen. No match means no pattern.
- **Every screen is generated with its app's context, whichever path makes it.** `app/Services/ScreenContext.ts` builds the brief (app name, sibling screens, shell contract, house-style digest) for both the planned run and a screen added later from chat. A new generation path must go through it, or the screen is designed as if it belonged to no app.
- **The conversation is written by the controllers, in code.** Every generation request records the ask and then what was done (`messages` table, `lib/agent-messages.ts`): the agent's reply and log are assembled from facts the pipeline already has — never from a model — and each agent message points at the snapshot taken before its change, which is what makes "Undo this step" exact. A new way to change a screen must write its message, with `versionId` or `created`, or it cannot be undone from the chat. The one exception is stepping between a screen's versions with the frame's `‹ ›` (`screens.version_id`): the opposite arrow is its undo, and every edit path starts from what the frame shows.
- **The chat has one truth for "something is running"** (`running` in `routes/p.$projectId.tsx`): the composer's send button is the Stop button while it is true, Esc stops, and a message typed meanwhile is queued and sent when it ends. What the agent is doing is shown from the pipeline's events (`ActivityCard`) — never from a model's words — and the same facts land in the message's log. A planned run started with `gate` stops at the plan (`PendingPlans`, in memory) and is drawn only on approval, with the person's edits applied by `editPlan`; without `gate` (the eval, the old API) it plans and draws in one run, and the ask is written once either way.
- **Elements are addressed by ids that are computed, not stored.** `annotateElements` (lib/element-ops.ts) is deterministic and idempotent; the browser runs it on stored HTML to render and the server runs it on the same stored HTML before any element edit, so both agree on `button-3` without it ever being saved. Every element edit — by hand or by model — must start from `annotateElements(screen.html)`. Hand edits splice the source (lib/html-tree.ts) so the rest of the screen stays byte-identical.
- **A streaming screen is never a srcdoc swap** (`lib/stream-frame.ts`, `lib/partial-html.ts`): the preview iframe opens once and its body is morphed from posted, repaired HTML; nothing (bridges, listeners, audits) is appended to a partial document. Photos and height arrive while it streams (`screen_image`, `od:stream:height`); plan frames are keyed by the screen id the server assigns up front and canvas frames are ordered by id, because moving an iframe in the DOM reloads it. `eval/stream.check.ts` measures code/blank frames, loads, photos and height on recorded streams.
- **A frame only trusts messages from its own iframe.** Every `ScreenFrame` listens on the same `window`; a handler that skips the `e.source === iframeRef.current.contentWindow` check answers every other frame's messages too. Anything a frame posts is untrusted input and is validated before it changes state or reaches the database.
- **A deleted screen keeps its row too** (`deleted_at`), so Cmd+Z can bring it back with its versions. `Screen.forProject` / `positions` leave deleted rows out; `find` / `findInProject` still return them (that is how restore and revert reach them), so a new listing query must filter `deleted_at IS NULL` itself.
- **Every canvas action is undoable from the keyboard** (`lib/undo-stack.ts`): an action either records its inverse (`pairStep`) or writes a conversation message, which the route turns into a step whose undo and redo are both "revert the latest message of the chain" (`messageStep`). A revert message records what it did in the same shape as the message it reverted, so reverting it is the redo. A new action that changes saved state does one of the two, or Cmd+Z will skip over it.
- **A screen that failed to generate keeps its row** (`html = ''`, `error`, `spec`), so it holds its slot on the canvas and can be retried in place. Code that lists screens for display, export, preview or measurement skips rows with empty `html`. `spec` is what a screen was planned to be and is never overwritten; `prompt` is the last instruction.
- **The bottom bar has a shape, and the app picks it once** (`ShellService.navStyle`): the app's character narrows the candidates (`NAV_SETS` by design system, then by app type — a tool wears `bar` or `contrast`, a consumer app `island` or `pill`) and the app's name picks one of them with the same FNV-1a hash the blueprints use — never by the model, and never per screen. The project's name is the app's name, so a screen added later from chat builds the same bar. `navClearance(style)` is the single source of the bottom padding the prompt asks for and the normalizer applies. The active tab is a shape (a tinted pill, or a dot under an icon-only tab), not just a colour.
- **Code may add to a screen and may substitute inside it; it does not re-lay it out.** What we inject is ours (tokens, fonts, icons, the shell, the kit sheet, a chart or a photo the model asked for with a slot) and what we substitute has exactly one right answer (a font below the minimum, a brand colour used as text, a tap area). Moving a box the model positioned is a third thing, and it is guesswork: it took three attempts at repositioning a floating action button to find that no static rule can know what a fixed element sits on. When a fix means changing geometry, the lever is the input — the blueprint, the pattern, the contract — or the finding is left in place and measured. `lib/render-audit.ts` measures; it never edits.
- **A craft rule with one right answer is applied in code, as a zero-specificity default** (`autofixScreen`'s `data-od-craft` sheet): tabular figures, balanced headings, a focus ring, press feedback inside a reduced-motion query, an outline on photos. `!important` is never used there, so a screen that styles the same thing itself still wins. The prompt (`craft/mobile.md`) carries only what needs judgement — and every new rule there replaces a weaker one, because the mobile system prompt is capped at 24 000 characters.
- **A text token has to be legible on the surfaces it sits on.** Every design system's `--fg`, `--fg-2`, `--muted` and `--meta` clear 4.5:1 against `--bg` and `--surface`, checked in `new-features.check.ts`. This is not cosmetic: `craft/mobile.md` tells the model which token to use for which kind of text, so a token under AA makes every generated screen fail with it.
- **A repair never grows the drawn box.** A tap target is given by an invisible `::after` (`autofixScreen`), never by a `min-height` on the element — a 44px button inside a 44px rail pushes itself out of its own track. The same holds for anything else the audit reports: the fix goes in code, at the layer that knows the box.
- **Platform numbers live in `lib/hig-rules.ts`** (min font, tap target, contrast, tabs). The linter, `autofixScreen` and the render audit read them from there; the prompt only says them in words. A fix with exactly one right answer (tiny text → 11px, an icon button's 44px hit area) belongs in `autofixScreen`, not in the prompt.
- **Shell markup uses inline styles only**, never Tailwind classes. Whether a screen loads Tailwind is the model's choice; a class-styled nav collapsed off-screen on a plain-CSS screen.
- **Never hardcode a light surface** (`bg-white`, `#fff`) in shell markup. Use `var(--surface)` / `var(--border)` or dark design systems break.
- **Icons are `<i data-lucide="name">`.** The model must not hand-draw icon SVG.
- **Mobile prompts read `design-systems/<id>/STYLE.md`, never `DESIGN.md`.** The style card describes the look only: no brand, product or mascot names, colours only as `var(--token)` from that system's `tokens.css`, at most 60 lines, fixed section outline. `services.check.ts` enforces this for every system, so a new design system needs a card that passes it. `DESIGN.md` is the source the card is distilled from and is never sent to the model. The product draws phone screens only — every project is created `mobile`, and there is one skill (`skills/mobile-screen`).
- **The mobile system prompt has a budget: under 24 000 characters, enforced by a test.** Craft guidance for phone screens lives in one file, `craft/mobile.md` (at most 150 lines, each rule a decision plus its reason). A new rule replaces a weaker one; it is not appended.
- **Nobody picks a style before there is anything to look at** (DS-01/DS-02). The composer has no system picker; `DesignSystemService.autoFor(brief, appType, seed)` decides — a brand the brief names as a comparison ("like Notion", "Airbnb-style") wins, then a style word, otherwise the app type offers two or three of the systems written for a phone (`category: "Mobile"` in the manifest: Nova, Lumen, Graphite, Ember, Volt) and the project id picks one, so the same brief twice is not the same app twice. The brand packages were written for websites and are not in the automatic choice. A system keeps its own colours: the planner no longer invents a palette, because one laid over an authored system replaced its measured ink ramp with a 60%-saturated one. The choice stays changeable in the Theme panel: first the result, then the tuning.
- **A reference picture decides the look, and it decides it first** (IMG-01/IMG-02, `ReferenceService` + `matchSystem`). One vision call reads the picture into a structure — accent, background, corners, display type, mood, and a paragraph on composition — and then code does the deciding: `matchSystem` scores the systems written for a phone against it (background lightness and accent hue dominate; mood words and the card's own Type section break ties) and `themeFromReference` sets the accent and the corners. All of it runs before a single screen is drawn, because a system chosen from the brief's words has nothing to go on when the brief is "same as in the image". The composition paragraph then rides every screen brief; the picture itself is never stored and never sent again.
- **A reference picture rides one request, never a run** (LLM-02, `lib/ref-images.ts`): `deepseek-flash` reads images itself, so there is no second provider. An image is charged as prompt tokens and never returns as a cache hit, which is why it is attached to the single generate call that asked for it — at most two, 1 MB each, `png/jpeg/webp` data URLs only, no remote URL (the server does not fetch on the model's behalf) and no SVG. `refImageNote` tells the model the picture is direction, not content: layout, spacing, type scale and mood, while the app keeps its own data, copy and tokens.
- **Images are slots.** The model writes `<img data-od-img="what the photo shows" alt="…">` with no `src`; `ImageService.resolveImages` fills it from Pexels before the screen is saved, caching by normalised query in `image_cache`, and locks the box (`object-fit`, `aspect-ratio`) so a photo never decides layout. Only `https://images.pexels.com/` URLs are accepted; the API key stays server-side. A slot with no photo becomes a token-coloured block, never a broken image. Any new path that saves generated HTML must call `resolveImages`.
- **Shared components live in `kit/od-kit.css`** (tokens only, `od-` block/element/modifier names). The normalizer injects it only into a page that uses an `od-` class, ahead of the page's own styles. A new component needs a sample in `kit/samples.ts` (the test checks both directions) and a look in the gallery (`node --import ./eval/alias-hook.mjs kit/gallery.ts`). Accent or status colour used as text goes through the `--od-*-text` mixes, never raw `var(--accent)`.
- **The render audit sees what code cannot** (`lib/render-audit.ts`): overflow, clipped text, small targets, low contrast, overlaps and text covered by a floating button, each with the offending element's `data-od-id`. It is a measurement, run by `eval/audit.ts` in headless Chrome inside a real 390px iframe and reported in every eval run as `metrics.audit`; its output goes through `parseAudit`. **The findings are never shown to the person, and nothing is repaired automatically**: the first generation is what it is. The canvas does not run it — an in-frame audit nobody listened to was removed, as was the automatic-repair route.
- **Charts are slots.** The model writes `<div data-od-chart="bar|line|area|sparkline|donut|ring|heatmap" data-values="…" data-labels="…">` and `lib/charts.ts` (called from `autofixScreen`) draws it from the data with token colours. The model never draws a chart; `charts.handDrawnScreens` in the eval counts the ones it did. **Maps are slots too** (`<div data-od-map data-pins data-route data-you>`, `lib/maps.ts`); an image slot asking for a map photo is converted before photos are looked up. A slot's default size is a zero-specificity `:where()` rule, never inline, so a size the page sets by class wins (image, avatar, logo and map slots alike).
- **Fonts are declared per design system** as `@import` in `design-systems/<id>/tokens.css` and injected by the normalizer. Every family in that URL must appear in a `--font-*` stack. Validate any new Google Fonts URL with curl; a weight the family lacks makes the whole request 400.
- **The studio has one warm palette, in `src/styles.css`** (UI-01): a single sand ramp that light and dark both take their surfaces from, and a brand colour used on a handful of controls — never as a surface, because the screens on the canvas are the colourful thing. No chrome value is a chroma-zero grey or pure black, and a test in `new-features.check.ts` keeps it that way. A screen on the canvas is drawn without a card around it (`--canvas`/`--canvas-dot` are the canvas's own tokens), and the Theme panel can show a colour without saving it (`onPreview` → `themePreview`, which the frames render instead of the saved theme).
- **Theme overrides are applied at render time** over stored HTML (`lib/theme-override.ts`); stored screens are never rewritten. Only validated values reach CSS — sanitize at every boundary.
- **The eval harness runs the real controllers, never a copy of the pipeline.** `eval/run.ts` calls `PlanController.stream` in-process against a throwaway SQLite file (`DB_PATH`), so it measures what users get. `eval/alias-hook.mjs` is what lets plain `node` resolve `@/` outside Vite. Metrics in `eval/metrics.ts` are deterministic; every known failure mode gets a counter there before it gets a fix.
- **Shell and injected markup carries markers** (`data-od-shell`, `data-od-icon`, `data-od-font`, `data-od-tab`, `data-od-back`; the model adds `data-od-link`, `data-od-img`, `data-od-avatar`, `data-od-logo`) so the linter and the preview recognize canonical output.

- **The design systems and the playbook are public** (`/systems`, `/systems/$id`, `/playbook`, MKT-06): unauthenticated read-only server functions, no project or user touched; a system page renders that system's own style card and draws the palette with `designSystemSample` in a sandboxed iframe. `src/content/playbook.ts` is the public copy of what the code enforces — when a rule moves or changes, that file changes with it.

## Accounts and limits

- **Server functions and API routes check the caller; controllers trust theirs.** Every function in `server/fns.ts` runs `requireUser` / `requireProject` / `requireScreen` (`server/auth.ts`) and validates its input with `server/validate.ts` before calling a controller; the streaming routes go through `server/guard.ts` (sign-in, ownership, same origin, limits). A new server function does the same, or it is an open door. Controllers stay callable directly for the eval and the tests.
- **Stored screen HTML is never served as a page of our origin.** Dashboard thumbnails come from `/api/thumb/$screenId` (owner only, 404 otherwise) with `Content-Security-Policy: sandbox allow-scripts` and are framed with `sandbox="allow-scripts"`; any new route that returns generated HTML does the same.
- **The admin panel checks on the server, every call.** `/admin/*` routes and every function in `server/admin-fns.ts` go through `requireAdmin()` (a non-admin gets the same 404 as a missing page); an admin is `user.role = 'admin'` or an email in `ADMIN_EMAILS`. Every admin write goes through `AdminController`, which logs it in `admin_actions`. Runtime switches (pause, limits, budget, per-user limits) live in `settings` and are read through `UsageService.limits()` — an env `GENERATION_PAUSED=1` still wins. A banned user counts as signed out in `userFrom`.
- **A planned run outlives its page** (`PlanRuns`): closing or reloading the tab stops the events, not the drawing; only Stop (`/api/stop-plan`) ends it, and `guardGeneration` releases the one-at-a-time lock when the run finishes (`X-OD-Detached` + `finish`). A single-screen edit still stops with its page.
- **Credits are a ledger, never a number on the user** (`credit_ledger`, `app/Models/Credit.ts`, BIL-04): every grant, hold, refund and purchase is a row with a whole `delta`, and a balance is the sum. A row caused by something outside an action (a payment event, a signup) carries a `ref`, which is unique, so a webhook delivered twice grants once. An admin changes a balance only by adding a row (`grantCredits`, logged in `admin_actions`) — never by editing one.
- **A stranger gets 404, never 403** for someone else's project — its existence is not confirmed.
- **Every model call is logged** (`llm_calls`, via `LlmService.onLlmCall` + `UsageService`), attributed to the request's user, project and action through `AsyncLocalStorage`, with the model that answered and its cost from that model's own price. One guarded request is one action (`action_id`, minted in `guardGeneration`); `UsageService.actionCost` is what the action really cost, which is what a credit is measured against. The limits (`UsageService.refusal`: calls per user per day, one generation at a time, daily budget, `GENERATION_PAUSED`) read that table. A new generation path must run inside `guardGeneration` or it escapes both.
- Secrets live in `.env` only: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID/SECRET`. The magic link is logged to the console in development and refused in production until an email provider exists (EML-01).
