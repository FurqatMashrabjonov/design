# Working agreement

This is an MVP. The rules below exist so scope stays fixed. Read them before writing code.

## Scope rules (highest priority)

1. **The Notion database ["Vazifalar"](https://app.notion.com/p/55b59dbe8eb4414490bd2baa79cc6540) is the source of truth for what to build.** Work only on rows whose `Doira` is `MVP` and whose `Holat` is not `Tayyor`, in `Tartib` order. The plan is written in Uzbek: `Doira` = scope (`MVP` / `Keyin` / `Bekor`), `Holat` = status (`Rejada` / `Jarayonda` / `Bloklangan` / `Tayyor`).
2. **No feature that is not in the roadmap.** If you think of one (or the user asks for something not listed), do not build it. Add it to the Notion plan with `Doira` = `Keyin`, say so in one line, and ask whether to move it to `MVP`.
3. **Finish before starting.** Do not begin a new row while another is `Jarayonda`.
4. **Bug fixes, tests, and refactors needed to finish an MVP row are in scope.** Cleanup that serves no MVP row is not.
5. Do not propose new features unprompted while an MVP row is open. Recommendations are welcome only when the user asks "what's next" or asks for research.

## Log every change

After each completed change, before reporting it done:

- Add an entry to `docs/CHANGELOG.md` (newest first): what changed, files touched, how it was verified.
- Set the row's `Holat` to `Tayyor` in Notion, and regenerate the `docs/ROADMAP.md` snapshot.
- If it changes how the system works, update the "Architecture rules" section below.

`docs/ROADMAP.md` is a read-only snapshot of that database so the plan stays readable without Notion. When Notion is unreachable, work from the snapshot and reconcile once it is back. Related Notion pages: the [plan overview](https://app.notion.com/p/3e039db48ef981bb9c26e3b652eeebaa), the [Modullar](https://app.notion.com/p/cea1e64dba26420d8a3d5088f9272201) database (one page per module, with its tasks), and the [competitor notes](https://app.notion.com/p/3e139db48ef981f2adb7f6d10f919ed5).

Starting a session on a new machine or after a break: read `docs/HANDOFF.md` first — current state, open issues, and setup.

## Commands

```
npm run dev          # vite dev server (http://localhost:3000 by default; pass --port to change); needs Postgres (DATABASE_URL, default postgres://localhost:5432/design)
npm run check        # service, database and feature tests (plain node scripts, no framework)
npx tsc --noEmit     # typecheck
npm run build:runtime  # build the screen runtime (React + Konsta + @od/kit + icons) into runtime/dist; check builds it if missing
npm run eval -- --label <name> [--vs <label>] [--only id,id] [--reshoot]   # eval/briefs.json through the real pipeline -> eval/out/<label>/
npm run judge -- <label> [--vs <label>|best] [--best]                      # vision judge (rubric + pairwise both orders) on a run's screenshots
node --env-file=.env --import ./scripts/alias-hook.mjs scripts/social-posts.ts --project <id>   # launch post images in the brand style (the social-posts skill)
```

A change is not done until `npm run check` and `npx tsc --noEmit` are clean. UI changes must also be exercised in a real browser (golden path plus one edge case) — type checks do not prove a feature works.

A change to generation (skill, kit, examples, planner, compiler) is judged on the eval set, not on one hand-picked prompt: `npm run eval -- --label <what-changed> --vs <previous>` (8 briefs on the real default model — GPT-6 Luna, about $0.10 a run — ~8 min; `--model <id>` runs every call site on another model; `LLM_PROVIDER=claude-cli` only for a free smoke run, since Haiku's results do not transfer) prints the metric deltas (build rate, crash rate, tokens and seconds per app, and source counts: Konsta parts, kit figures, emoji, palette colours, gradients, motion, nav calls, onboarding) and writes `index.html`, a contact sheet of every screen. Then `npm run judge -- <label> --vs <previous>` for taste. A kit fix is re-rendered over stored screens with `--reshoot` (no model calls).

## Model policy

**Which model runs is an admin setting per call site** (LLM-04/07): `llm.model.plan`, `llm.model.screen`, `llm.model.edit` and `llm.fallback`, read at call time (cached ~10s). Every model has an adapter (DeepSeek, Gemini and OpenAI through OpenAI-style Chat Completions — GPT-6 as a reasoning model: `max_completion_tokens`, no temperature, `reasoning_effort: none`; Anthropic through the Messages API, where a model that cannot switch thinking off, Opus 5.5, runs at effort `low` — `MODELS` beside `PRICES` in `LlmService`), a `PRICES` row and a `CREDIT_PRICES` row, which the credit price test holds to the model's own worst-case cost; a credit is charged at the model the action's site is set to. A 429 that says how long to wait is waited out and retried on the same model (twice at most; OpenAI's per-minute token limit). A call that fails before its first token is retried once on the fallback, or on the same model when no fallback is set (a dropped connection once left an app with no plan); nothing switches mid-stream; each attempt is logged under the model that ran. The default everywhere is GPT-6 Luna (`gpt-6-luna`, reasoning effort `none`; LLM-08, 2026-09-29: on the eval it beat DeepSeek V4.1 Flash 6–0–2 at about the same price, with −35% output tokens), and with no fallback set by the admin the fallback is DeepSeek V4.1 Flash, a second provider; `LLM_MODEL` changes the default (the tests pin `deepseek-flash`, whose shape their stubs answer in). DeepSeek V4.1 Flash is `deepseek-flash` (re-pointed from V4 to V4.1 on 2026-09-10 at the same price), not `deepseek-v4-pro` (`deepseek-flash`, which DeepSeek re-pointed from V4 to V4.1 on 2026-09-10 at the same price) — not `deepseek-v4-pro`. The id is pinned in `LlmService`, because `deepseek-flash` thinks by default and an alias can be re-pointed. (The old `deepseek-chat` id is an alias of exactly this configuration.) **Thinking is decided per call site, not once**: off for the six or seven screen calls, because reasoning tokens bill as output and output is the expensive half of an app (~47k of ~86k tokens; one plan measured 8 924 tokens / 89s with it on against 2 075 / 17s with it off), and off for the planner too, which an A/B settled rather than taste: on the same brief it produced a smaller plan for five times the output tokens and five times the wait (6 screens / 8.8s / 2 283 tokens against 5 / 43.6s / 10 658), and at the old 4 000-token cap the reasoning ate the JSON and two briefs drew nothing at all. `LLM_PLAN_THINKING=1` keeps the question askable — with it the planner's cap rises to 12 000, because reasoning spends the same budget as the answer. The price table (`PRICES`, by model, with `isPeak`) holds each provider's real list price and knows that DeepSeek's peak costs double, because the daily budget guard and credit prices spend against it; `costOf` refuses a model with no row instead of calling it free, and the process refuses to boot on a `DEEPSEEK_MODEL` it cannot price. Push correctness into deterministic code instead of asking a model to hold a contract — see the next section.

For local testing only, `LLM_PROVIDER=claude-cli` routes generation through the developer's own Claude Code login (`claude -p`) so trying things costs no DeepSeek balance. It runs on Haiku 4.5 by default — local testing is about seeing a change land, not about quality — and `CLAUDE_CLI_MODEL` overrides that when a run needs the bigger model. Thinking is off there as it is on DeepSeek (`MAX_THINKING_TOKENS=0` in the child's environment): with it on, one plan cost 8 900 output tokens and 89s instead of 2 100 and 17s, which reads as a hang. It refuses to run with `NODE_ENV=production`. Evals may run on it (`run.json` records the provider; a run is only compared with runs on the same provider) — such a result says how a code change moves quality, and key results are re-checked on DeepSeek before launch.

## Architecture rules

- **Screens are React JSX on Konsta UI v5 (iOS theme) + Tailwind v4 — there is no HTML pipeline** (KON-00, 2026-09-28; the old HTML engine is in git history). The model writes one screen as a default-exported component; `app/Services/ScreenCompiler.ts` parses it (@babel/parser), refuses any import outside `react`, `react/jsx-runtime`, `konsta/react`, `lucide-react`, `@od/kit` and any banned identifier (fetch, eval, storage…), transforms JSX with rolldown and builds the screen's own Tailwind CSS. Model code never runs in the server's own process; the one place it runs on the server is headless Chrome for the render check (KON-13, below), under a CSP with no network. A source that does not build gets one retry with the compiler's errors (`drawScreen` in `PlanController`), then the screen is a failed slot.
- **What the model gets wrong with Konsta is fixed or reported in code, not in the prompt** (HIG-10, `lib/jsx-lint.ts`, run in `drawScreen` before the compiler). **The generated source is never rewritten by our code** (the owner's rule, 2026-10-05, LNT-01: `lintJsx(src, { apply: false })` in `drawScreen`): a rule with one right answer is reported to the model with its exact fix (`AS_FINDING`) and goes into the one repair rewrite below, alongside the render check's findings — the rules: a `ListItem link` draws its own chevron (a second is removed), text on a `tint()` wash is never white, a `Block` pads itself (no `px-4` on it), a lone `bg-white` gets its dark pair, text is never under 11px (HIG Caption 2), an icon-only `Button` is `inline` (Konsta buttons are full width, and two arrows beside a month title pushed it under them). A rule that needs a decision is reported — `ListItem`/`ListInput` outside a `List`, `BlockTitle` inside a `Block`, a `List` or `Card` inside a `Block`, more than two large buttons, an emoji in a control, a fixed bottom bar under the tab bar — logged as `[jsx-lint]` and counted by the eval (`hig`, `higByRule`). The compiler refuses a `<Tag>` nothing declares and the runtime does not have (it would crash the frame), so the screen gets its one retry; locals, destructured params and built-ins like `Number()` are not tags. A new failure mode gets a lint rule (with the fix spelled out for the model) before it gets a prompt sentence. A kit part takes the forms a model writes (a date as a Date, 'YYYY-MM-DD' or a timestamp — `asDate` in `runtime/kit/blocks.jsx`), because the model's code is not corrected after it is written. Measured (lnt01 against blk03): the judge preferred it 4–2–2, at +40% output tokens (more repairs run) and 11% of screens with a problem left against 3%.
- **A drawn screen is checked before anyone sees it, and repaired once** (KON-13 + HIG-15, `drawScreen`): after the lint and the compiler, `RenderAudit.auditScreen` opens it in headless Chrome (a private server on 127.0.0.1, a random token, CSP `connect-src 'none'`, images only from Pexels; `?static`, a phone wide and as tall as its content) and the kit measures it (`lib/render-audit.ts`, answered on `od:audit`): a box past the phone's edge, text cut off, text over text, text under a card, near-invisible text, half a phone empty. Those findings plus the lint's reported ones and FCT-01's fact check (`lib/fact-check.ts`: a person's XP or streak on the screen that APP DATA does not have, nor the gap or sum of two of its values — only those two facts, because distances and steps flagged honest numbers) go into one rewrite; the rewrite is kept only if it builds and fewer problems are left. The chat log says `checked: N found, M left`. Measured on DeepSeek V4.1 (2026-09-29): most breakage was one Konsta trap (a `BlockTitle` pulls up the next box by `-mb-2`; with no `Block`/`List` under it, or one whose margin the model changed, it needs `!mb-2`) — since LNT-01 that is reported and the model fixes it in the repair. The page is measured as iOS and again as Material, switched in place (HIG-16); an Android-only finding is named so. Without Chrome the check is the lint alone; `RENDER_AUDIT=0` turns it off (the tests do); the eval measures every final screen either way (`problemsPerScreen`, `cleanShare`). Every headless Chrome the server starts — checks and KON-10's pictures — waits for one of `CHROME_MAX` slots (default 3; each is ~200–400 MB for a second or three), so many users generating at once slow down instead of starting forty browsers.
- **Legibility and the type scale are the kit's job, not the model's** (HIG-12). Apple's text styles are Tailwind utilities (`text-large-title` … `text-caption2`, plus `text-figure` for a hero number; `runtime/type-scale.css`, read by both `runtime.css` and `ScreenCompiler`, and copied into an export). Text on a filled colour takes its colour from `onColor` (`runtime/kit/on-color.js`: white while white clears 3:1, otherwise ink), which `Hero`, a solid `Tile` and `gradient()`'s default second stop use — so a yellow or mint card never carries white text, whatever the model writes (the lint drops `text-white` on a `Hero`). Kit code stays plain and self-contained under `runtime/kit/`, because the export copies that folder. The eval counts `adHocText` (`text-[Npx]`) against `namedText`.
- **The model learns Konsta from files, not from memory**: system prompt = `skills/mobile-screen-jsx/SKILL.md` (HIG-first, ≤8k characters: structure, one primary action, inset grouped lists, text styles, then colour, emoji and photos) + `konsta/KIT.md` + `konsta/USAGE.md` (HIG-13: right/wrong JSX for the mistakes the lint keeps seeing) + `konsta/PATTERNS.md` (OVL-01: one working pattern per Konsta part — sheet, action sheet, dialog, drawer `Panel`, popover, popup, toast, notification, FAB, search, controls, forms, chat — and "every primary action answers") + `konsta/REFERENCE.md` (generated by `scripts/konsta-reference.mjs`), and every screen brief carries one finished screen from `konsta/examples/` chosen by its kind (`exampleFor`: first-run → its onboarding layout, the first tab → dashboard (drawer from the avatar, a toast on check), other tabs → list (search, FAB, action sheet), pushed → detail (action sheet, confirm dialog), modal → sheet, a paywall modal → `paywall`). **The flow a top app shows** (PRM-02): the planner gives a consumer app one modal with id `paywall` (kept through the eight-screen cut like an asked screen), and the first-run screen ends on the kit's `SignInButtons` (Apple and Google with their real marks) instead of a lone Continue — no separate sign-up screen. **People are portraits** (PRM-01): `Avatar({ photo })` shows a Pexels portrait (looked up from `<Avatar photo>` and `avatar`/`photo` data keys), initials only until it loads; the planner gives every person a `photo: "portrait …"`. **A modal screen is drawn as an open bottom Sheet over the dimmed page** (OVL-01; closing it is `nav.pop()`), so a sheet shows on the canvas, the preview and in pictures — every other overlay starts closed. Before OVL-01, 182 eval screens had 0 drawers, toasts, popovers or FABs: the text named them, no example used them. The eval counts `overlays`. **The first-run layout is the code's** (ONB-01): five layouts — `slides`, `photo`, `quiz`, `value`, `showcase` (`ONBOARDINGS`, one example each, `konsta/examples/onboarding*.jsx`) — and `parsePlan` with the project id picks one of the three its style allows (`seededPick`, salted, like the colours), stored as `plan.onboarding`; the screen brief names it (`Layout: …`). With one example 7 of 7 eval apps opened on the same carousel whatever their style. A plan from before has none and keeps the carousel. The eval counts `onboardingKinds`. An example is the strongest lever on quality — it is copied for its build, never its data or palette. Prompts and planner live in `app/Services/JsxGenerator.ts`.
- **The bar is a top App Store app, not restraint** (2026-09-28): the skill asks for colour with confidence (gradient hero tiles, tinted tiles, coloured figures), emoji as content (item icons, awards, onboarding art — never in buttons, navbars or body text), motion (`vs-rise` stagger, `vs-float`, `CountUp`, `Confetti`) and a first-run onboarding for consumer apps. Measured on the eval: colours 1.7 → 6.3 per screen, emoji 0.6 → 4.2, onboarding 2 → 8 of 8 apps, at +50% output tokens and +43% time per app.
- **An app has one of five styles, and its colours are the code's** (THM-01, researched on 47 top iOS apps: Clean ~30%, Midnight ~25%, Vivid, Soft, Editorial ~15% each). The planner picks `style` from the five (by what the audience would expect) and names 2–4 palette keys (PAL-02: four at most, and they are a family — the seed's colour, the two hues nearest it, the one across the wheel — not consecutive colours of the set, which made a rainbow; the judge's coherence went 3.38 → 3.88); `parsePlan` with the project id as seed takes the palette colours from that style's own set, starting where the seed says (`styleColors` in `lib/app-theme.ts`, FNV-1a with a murmur finaliser — plain FNV's low bits gave two eval apps the same colours), and the accent is the first of them that darkens to white-text contrast in a few steps (PAL-01: each style's set is drawn in OKLCH at one lightness and chroma, yellows and limes a step lighter; darkening is in OKLCH with the chroma kept, at most 3 steps, else the colour that darkens least — RGB darkening turned Midnight's neons into dusty mustard) (an accent picked apart from the palette clashed with it) — the model never writes a hex, because shown eight iOS hues it put every app in the same eight. Every accent reads as a button with white text (≥3.5:1, tested). `appContext` gives every screen the style's card (`STYLE_CARDS`: how to compose; for onboarding only its tone — the layout is ONB-01's) and the same `const C = {…}` line. A midnight app starts dark.
- **A style is CSS variables, so switching it recolours every screen in place** (`runtime/kit/styles.js`, `applyStyle` in `mount` after the accent, also in the export): it sets Konsta's own surfaces (iOS `--color-ios-*-surface*`, Material `--k-color-md-*-surface*`), the kit's `--app-page/card/card-2/line/radius` behind the Tailwind utilities `bg-page`, `bg-card`, `bg-card-2`, `border-line`, `rounded-card` (in `runtime/type-scale.css`'s `@theme`, read by the compiler and the export), and the fonts (`data-app-font` / `data-app-display`: rounded for Vivid and Soft, a serif for Editorial's titles). A screen's own boxes use those classes; the lint turns `bg-white` (and its hard-coded dark pair) into `bg-card`. Every style's page and cards keep ≥7:1 with the label colour, light and dark (tested). Editorial is on warm paper (PAL-03: `#faf7f1` page, `#fffdf9` cards; a warm near-black in dark) — on pure white its cards vanished and the judge preferred the cream 3–0. **The eval shoots each app in its plan's style, Midnight dark** (`addPages` in `eval/run.ts`); before PAL-03 it shot every app on Clean's surfaces, so no style change was ever visible to the judge — runs before then are not comparable on surfaces and fonts. The Style & colour panel shows the five with a preview.
- **What the compiler can repair with one right answer, it repairs**: a Konsta component, kit export or lucide icon used but never imported is imported for it (a forgotten `BlockTitle` import crashed a screen). A screen that still throws shows "This screen crashed: …" (kit `Crash` boundary, and a catch around the module load) instead of a blank frame; the eval counts these as `crashRate`.
- **A reference picture rides the request that carries it** (REG-01, `lib/ref-images.ts`): at most two PNG/JPEG/WebP data URLs under ~1 MB each, checked at the edge (`parseRefImages`; a remote URL or SVG never reaches a model; the guard refuses a body over 3.2 MB). A planned app shows it to the planner (it picks the style from it) and to every screen call; an edit or an added screen shows it to that call; each call that sees it gets `REF_IMAGE_NOTE` (take its visual language inside the app's own style card and palette, never its text). The picture is not stored — the message's meta says `images: n`. From the dashboard it reaches the canvas through `sessionStorage` (`od:brief-images:<projectId>`), never a URL.
- **The plan is a contract checked in code** (`parsePlan`; HIG-17: screens the brief names are `asked` and survive the eight-screen cut — unasked pushed screens go first, then an unasked tab; `data` gives every fact one value app-wide; the planner is told today's date): 3–5 tabs with icons from `TAB_ICONS`, screens of kind `tab|push|modal|first-run`, one root screen per tab, tabs no screen opens pruned, a push with no parent goes back to the first tab, an accent that is not `#rrggbb` falls back. The plan is stored in `projects.plan`, tabs in `projects.navigation`, the accent in `projects.theme`; its `data` block rides every screen brief, so screens share names and numbers.
- **An app is one app: every screen reads and changes one store** (FUN-01…03, 2026-10-07, the owner's call: "every page must know the others and work"). After the plan and before any screen, `writeStore` (`JsxGenerator`, `STORE_SYSTEM`) has the model write the app's data layer — one plain module with `initial` (all the app's data, from the plan's `data`), `actions` (every change a person can make, read from the screens' specs) and `derived` (every value computed from the data; `(state, id) => …` for one item's value) — checked by `compileStore` (no imports, no browser APIs, no timers; one retry with its errors; a store that fails twice leaves the app on APP DATA) and kept in `plan.store`. Every screen brief carries it instead of APP DATA (`storeSection`), and a screen reads the app with `useStore()` from the kit (`runtime/kit/store.js`: state keys, derived values and bound actions in one object; an action runs on a copy and a throw keeps the old state; `state` itself is there too). Each screen's page gets the compiled store (`ScreenDocument`, `AppLook.store`, part of a picture's key); in the studio each frame has its own copy and the host keeps them in step (`lib/app-state-bus.ts`: a change posts `od:state`, the bus hands it to the app's other frames by the store's hash, a late frame asks with `od:state-hello`; in memory, so a reload starts from `initial`). A push carries params (`nav.push('habit', { id })`; `parseParams` keeps a few plain values; the preview posts `od:params` to the target frame, which reads `useNav().current.params`). The export ships `src/store.js` and keeps the state in localStorage. Quick tasks (add, edit, log, filter, confirm) are overlays on the screen they start from, not screens; `modal` is only a full-screen flow (the paywall). A complete app is up to `MAX_SCREENS` (12) screens, and a brief that names a count gets that many (`askedCount`). The kit's `ListItem` ignores a tap that landed on a control inside the row (a checkbox ticked and opened the detail). The render check reports a visible "Invalid Date", "NaN", "undefined" or "[object Object]" (`broken-value`). The eval counts `store` (share of screens on the store) and `handlers` (controls that answer a tap or input).
- **The source is stored as it was written** (`screens.html` holds the JSX; `isJsx` tells old HTML rows apart, which are served raw). `screens.slug` is the plan id that `useNav().push(slug)` and `reset(tabId)` address.
- **A screen runs on a prebuilt runtime** (`runtime/`, `npm run build:runtime` → `runtime/dist`, gitignored): React, Konsta, `@od/kit` (Ring, Rings, Bars, Area, Heatmap, Meter, WaterGlass, CountUp, Tile, Medal, Avatar, Glow, Dots, Confetti, `tint`, `gradient`, AppTabbar, useNav, `mount`; `?static` adds `vs-static` so screenshots show finished screens; KIT-20's blocks in `runtime/kit/blocks.jsx` — WeekStrip, MonthCalendar, StepTimeline, Carousel/PhotoCard, EmptyState, Skeleton*, PullToRefresh, Accordion, SwipeRow, Rating/RatingSummary, AvatarStack, Stories, CodeInput, SignInButtons, BentoGrid/BentoCard — hand-written and approved by the owner in a gallery (`gallery/*.jsx`, bundled by `scripts/kit-gallery.ts`) before joining; offered by the code one screen at a time (KIT-21, `BLOCK_HINTS`/`blocksFor` in `JsxGenerator`: a screen whose **name** says it does what a block does — Dates → MonthCalendar, Tracking → StepTimeline, Reviews → Rating, a habit app's Today tab → WeekStrip, Explore → Carousel, Inbox/Notifications → SwipeRow, Tracking/Map/Run/Delivery → RouteMap (KIT-23: a drawn map with the route, start, end and the courier or runner; the judge's most repeated complaint was a map drawn as an empty box), Club → AvatarStack, Verify → CodeInput, FAQ → Accordion — gets that block, two at most, in its own brief with how to call it). Listed for every screen they lost the judge twice and went unused; matched on a screen's spec they landed on profiles and leaderboards; matched on its name they sit where they belong; their classes reach the runtime stylesheet through its `@source` list, and the export copies the file) and one module per lucide icon, served by `/api/rt/v<build>/…` with CORS `*`. The build segment is the runtime's mtime, so a rebuilt kit is a new URL under the hour-long cache. A kit prop that takes a colour accepts only a CSS colour (`cssColor`); a Tailwind class there becomes the accent.
- **A screen's page is `/api/thumb/$screenId`** (`ScreenDocument`): import map + runtime CSS + the screen's CSS + its compiled code inlined as a blob module (a sandboxed page fetching it from us would go without cookies). Owner or admin only, CSP `sandbox allow-scripts`; `?dark=1`, `?v=<versionId>`, `?static`. The canvas, preview and dashboard frame it with `sandbox="allow-scripts"`; `ScreenFrame` adds `r=<hash of source>` so a changed screen is a new URL.
- **Where a screen is only shown, it is a picture, not the app** (KON-10, `ShotService`, `/api/shot/$screenId`): dashboard cards, the sidebar, the list view, admin pages and the chat's before/after load a PNG made once by the render check's own Chrome (`screenshotScreen`: framed at exactly 390×844 — headless Chrome lays a page out at least 500 wide and 87px short of its window — at scale 0.6, ~35 KB) and kept in `screen_shots` by a key of the source and the look (accent, dark, platform, style, tabs), so a changed screen or theme is a new picture and never a stale one; the ETag is that key. Pictures are warmed right after a screen is drawn or edited (`ShotService.warm`, off in tests with `SCREEN_SHOTS=0`), made on first ask otherwise, three Chromes at a time and one per key; `scripts/backfill-shots.ts` fills them for screens drawn before. The same access rule as `/api/thumb`. The canvas and the preview stay live. With no Chrome the `<img>` falls back to the live frame.
- **Photos are real and looked up at save** (KON-12, `PhotoService`): the model writes `<Photo q="what it shows">` (kit) and gives data items a `photo` query; `photoQueries` reads them from the source (literals and `photo`-like keys, never executed), `resolvePhotos` runs in `drawScreen` and fills `image_cache` from Pexels (PHT-01: the query's hash picks one of the five best results, so near queries — "runner portrait", "smiling runner portrait" — stop sharing one photo; the same query keeps its photo) (key via `SecretService`, only `images.pexels.com`, a miss is cached too), and `ScreenDocument` passes the cached URLs to `mount` — a render never calls Pexels, the model's code is never rewritten, and a query without a photo is a tinted block. Pexels allows 200 lookups an hour, so queries are normalised and shared through APP DATA; the eval keeps its lookups in `eval/photo-cache.json`. The preview no longer shows a Pexels credit (the owner's call, 2026-09-28); Pexels' API guideline asks for a visible link, so one belongs somewhere else in the product.
- **A frame is as long as its screen** on the canvas: the kit's `mount` reports the `.k-page` scroll height (`od:height`), `ScreenFrame` grows the frame (each version measured from a phone-tall viewport, so an edit can shrink it) and the canvas saves it to `screens.height` (clamped 844–5000) to lay out the next load. The preview stays one phone tall and scrolls.
- **The app's look is the app's, not the studio's** (KON-11, `lib/app-theme.ts`): `projects.theme` holds `{ accent, dark, platform: 'ios' | 'material', style }`, set from the canvas: platform (iOS | Android) and light/dark are a pill in the top bar (`AppLookSwitch`) because they are flipped all the time and their current value must show; the accent is the Colour panel on the rail (`ThemePanel`). Debounced save, one undo step per burst. The preview has the same switch, view-only. ## Accounts and limits

- **Server functions and API routes check the caller; controllers trust theirs.** Every function in `server/fns.ts` runs `requireUser` / `requireProject` / `requireScreen` (`server/auth.ts`) and validates its input with `server/validate.ts` before calling a controller; the streaming routes go through `server/guard.ts` (sign-in, ownership, same origin, limits). A new server function does the same, or it is an open door. Controllers stay callable directly for the eval and the tests.
- **Stored screen HTML is never served as a page of our origin.** Dashboard thumbnails come from `/api/thumb/$screenId` (owner only, 404 otherwise) with `Content-Security-Policy: sandbox allow-scripts` and are framed with `sandbox="allow-scripts"`; any new route that returns generated HTML does the same.
- **The admin panel checks on the server, every call.** `/admin/*` routes and every function in `server/admin-fns.ts` go through `requireAdmin()` (a non-admin gets the same 404 as a missing page); an admin is `user.role = 'admin'` or an email in `ADMIN_EMAILS`. Every admin write goes through `AdminController`, which logs it in `admin_actions`. Runtime switches (pause, limits, budget, per-user limits) live in `settings` and are read through `UsageService.limits()` — an env `GENERATION_PAUSED=1` still wins. A banned user counts as signed out in `userFrom`.
- **A planned run outlives its page** (`PlanRuns`): closing or reloading the tab stops the events, not the drawing; only Stop (`/api/stop-plan`) ends it, and `guardGeneration` releases the one-at-a-time lock when the run finishes (`X-OD-Detached` + `finish`). A single-screen edit still stops with its page.
- **Credits are a ledger, never a number on the user** (`credit_ledger`, `app/Models/Credit.ts`, BIL-04): every grant, hold, refund and purchase is a row with a whole `delta`, and a balance is the sum. A row caused by something outside an action (a payment event, a signup) carries a `ref`, which is unique, so a webhook delivered twice grants once. An admin changes a balance only by adding a row (`grantCredits`, logged in `admin_actions`) — never by editing one.
- **An action pays before it runs, and only for what it delivered** (BIL-06, `CreditService`, `server/guard.ts`). `guardGeneration` prices the request (`kindOf` + `CREDIT_PRICES`, by model) and holds the price before any model is called — a short balance is a 402 with `{ error: 'credits', needed, balance }`, and nothing is written. When the action ends, `settle` gives everything back if none of its model calls succeeded; a planned run pays back each screen it did not draw (failed or stopped) at a screen's price. A refund never exceeds what the action still holds, so settling twice is harmless. A new generation route goes through `guardGeneration` or it is free.
- **Money arrives only through a verified webhook** (BIL-09/10/11, Polar — Stripe does not open accounts in Uzbekistan). Checkout and the billing portal are the provider's hosted pages (`PolarService`), tied to our user by `external_customer_id`; products are found by `metadata.od` (`PRODUCTS` in `lib/credit-prices.ts`, created by `scripts/polar-products.ts`), never by pasted ids. `/api/polar-webhook` believes nothing before its Standard Webhooks signature (`lib/standard-webhooks.ts`, five-minute window). A pack is granted on `order.paid` with ref `order:<id>`; a plan is a `subscriptions` row that every subscription event rewrites, and its credits are granted per month of the plan (`CreditService.refresh`, ref `sub:<id>:<month>:<product>`, yearly plans monthly too) — before each new month, what is left of the last plan grant lapses; packs never lapse. `refresh` runs wherever a balance matters (the guard, `getCredits`, webhooks), so a renewal needs no scheduler.
- **The account's money has one page** (BIL-21, `/billing`, `BillingController.page`): the plan in force and when it renews or ends, this month's plan credits left beside the pack credits that never lapse (plan credits are spent first, so "left" is the last grant minus what was used since), changing plan monthly or yearly, packs (subscribers only), the provider's portal as one button, and the last 20 ledger rows. Account → Billing opens it.
- **Upgrade is offered where people work** (BIL-22…24): the dashboard sidebar's `UpgradePanel` — three rotating tips (export, iOS/Android, share link), the plan with this month's plan credits as a bar, and one action (lime Upgrade on Free, Buy credits on Starter, none on Pro); the upgrade dialog has the Monthly/Yearly switch and names the current plan; `LowCredits` puts one line above the dashboard prompt and the canvas composer once the balance cannot pay for a whole app.
- **A checkout that cannot open says so plainly** (BIL-25): `BillingController.checkout` turns any provider failure (an account still under review, no token, a missing product) into the one marker `PAYMENTS_CLOSED`, keeping the provider's reply in the server log; `buy()` opens `PaymentsSoonDialog` (mounted in the root beside `CreditsDialog`) — "Payments open in a few days" — whose button puts the signed-in person on the waitlist (`ref` `payments`, note `wants <product>`). Admin → Settings → Payments shows the provider's own verdict (`PolarService.status`: the organization's `checkout_payments` and how many products are set up).
- **A plan's limits are code, not copy** (BIL-14, `PLAN_LIMITS` in `lib/credit-prices.ts`, `CreditService.limitsFor`): Free 1 project, Starter 5, Pro unlimited, and export (zip, HTML, Figma) unlimited on paid plans; an admin is not limited. The project count is refused on the server in `ProjectController.store` (every way a project is made passes it). **Free has `FREE_EXPORTS` (3) exports in all, counted on the server** (PRC-02, `export_uses`, `CreditService.useExport` under a per-user advisory lock so two at once cannot both take the last try): `/api/export` checks `exportsLeft` first and takes a try only once the file is built; a Figma copy, built in the browser, claims one first (`claimFigmaExport`); a refusal is the 402 → upgrade dialog. /pricing lists only what the code keeps.
- **Prices are data shared by server and browser** (`lib/credit-prices.ts`: `CREDIT_PRICES`, `PLANS`, `SIGNUP_CREDITS`). The browser never computes a charge; it shows the balance (`CreditsBadge`, the dashboard card) and reloads it when any generation ends (`creditsChanged` in `generate.ts` / `generatePlan.ts`). A 402 from a guarded route becomes `OutOfCredits` (`failFrom`) and opens the one `CreditsDialog` mounted in the root — never a toast (`reportError` stays silent for it).
- **A stranger gets 404, never 403** for someone else's project — its existence is not confirmed.
- **Every model call is logged** (`llm_calls`, via `LlmService.onLlmCall` + `UsageService`), attributed to the request's user, project and action through `AsyncLocalStorage`, with the model that answered and its cost from that model's own price. One guarded request is one action (`action_id`, minted in `guardGeneration`); `UsageService.actionCost` is what the action really cost, which is what a credit is measured against. The limits (`UsageService.refusal`: calls per user per day, one generation at a time, daily budget, `GENERATION_PAUSED`) read that table. A new generation path must run inside `guardGeneration` or it escapes both.
- **A coding agent works through MCP with a personal API key** (MCP-01, `POST /api/mcp`, `McpService`): stateless Streamable HTTP; `Authorization: Bearer ss_…` is a key from `/connect` (`api_keys` keeps only its SHA-256; `userFromApiKey` applies the same ban and waitlist rules as a session). Each request builds a server bound to that person; a tool sees only their projects (else "not found"), and a tool that calls a model goes through `guardGeneration(request, run, user)` — the third argument skips only the cross-site and session checks, never limits or credits. An export is a 10-minute signed link (`lib/signed-link.ts`) to `/api/export`, which accepts `?k=`, so the plan rule and Free's count hold. A new tool reuses a controller; it never reaches the database around one.
- **Provider keys are entered in the admin panel** (ADM-13, Settings → API keys; `SecretService`): DeepSeek, Gemini, Anthropic, OpenAI, Pexels, Polar token and webhook secret, Resend. A key saved there wins over `.env` and is stored sealed (AES-256-GCM, `app/Services/secret-box.ts`) with the master key `SECRETS_KEY`, which lives only in the environment — the database alone reads nothing, and losing `SECRETS_KEY` means re-entering the keys. The browser only ever receives a key's last four; the admin log records the last four; "Test connection" returns an outcome, never a provider's body. Code reads a key through `SecretService.get` (LlmService through `setKeySource`, so its plain-node tests need no database) — never `process.env` for a provider key.
- **The email sign-in link is a switch** (AUTH-10, `magicLinkOn` in `AuthService`): off in production for now (Google only, the owner's call 2026-10-04), on in development; `MAGIC_LINK=1` turns it on (also the way back in if Google sign-in ever breaks), `MAGIC_LINK=0` off. Off means refused in `sendMagicLink`, not only hidden on `/login`.
- Secrets that stay in `.env` only: `SECRETS_KEY`, `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID/SECRET`. **Every email goes through `EmailService`** (EML-01, Resend over plain HTTPS: `RESEND_API_KEY` in the panel or `.env`, `EMAIL_FROM` on the domain verified in Resend with SPF/DKIM): the magic link (AUTH-04) and the waitlist confirmation (WLT-01), each a template in `lib/emails.ts` (html + text, inline styles, escaped). With no key, development prints the mail to the server log (`devMail`) and production refuses — nothing claims to be sent that was not. A mail that fails never fails what caused it, except sign-in, where the link is the point. **EML-03, Admin → Email:** every mail is a row in `emails` (sent, failed, logged); the system emails' words are the admin's (`settings` `email.template.<kind>`, defaults in `SYSTEM_EMAILS`, rendered by the one `renderEmail` the editor previews with, in a sandboxed iframe); a bulk send (`EmailService.campaign`: waitlist, all users or one person) skips who unsubscribed (`email_suppressions`), carries a signed unsubscribe link (`/unsubscribe`, HMAC of the address, one button so a mail scanner changes nothing) and a `List-Unsubscribe` header, is capped at 100 and the 24-hour limit of the free plan, and is paced for Resend's 2 requests a second. A sign-in link is transactional: it reaches someone who unsubscribed and carries no unsubscribe link.

## Git

- Commit and push only when the user asks.
- Pushing over HTTPS needs the GitHub CLI credential helper:
  `git -c credential.helper='!gh auth git-credential' push origin <branch>`
- Never commit `.env` or `data.db*` (both are ignored). `data.db` is the pre-Postgres SQLite file, kept as a backup; `scripts/sqlite-to-pg.ts` copies one into an empty Postgres.
