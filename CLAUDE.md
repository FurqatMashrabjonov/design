# Working agreement

This is an MVP. The rules below exist so scope stays fixed. Read them before writing code.

## Scope rules (highest priority)

1. **The Notion database ["Vazifalar"](https://app.notion.com/p/55b59dbe8eb4414490bd2baa79cc6540) is the source of truth for what to build.** Work only on rows whose `Doira` is `MVP` and whose `Holat` is not `Tayyor`, in `Tartib` order. The plan is written in Uzbek: `Doira` = scope (`MVP` / `Keyin` / `Bekor`), `Holat` = status (`Rejada` / `Jarayonda` / `Bloklangan` / `Tayyor`).
2. **No feature that is not in the roadmap.** If you think of one (or the user asks for something not listed), do not build it. Add it to the Notion plan with `Doira` = `Keyin`, say so in one line, and ask whether to move it to `MVP`.
3. **Finish before starting.** Do not begin a new row while another is `Jarayonda`.
4. **Bug fixes, tests, and refactors needed to finish an MVP row are in scope.** Cleanup that serves no MVP row is not.
5. Do not propose new features unprompted while an MVP row is open. Recommendations are welcome only when the user asks "what's next" or asks for research.

## Log every change

After each completed change, before reporting it done:

- Add an entry to `docs/CHANGELOG.md` (newest first): what changed, files touched, how it was verified.
- Set the row's `Holat` to `Tayyor` in Notion, and regenerate the `docs/ROADMAP.md` snapshot.
- If it changes how the system works, update the "Architecture rules" section below.

`docs/ROADMAP.md` is a read-only snapshot of that database so the plan stays readable without Notion. When Notion is unreachable, work from the snapshot and reconcile once it is back. Related Notion pages: the [plan overview](https://app.notion.com/p/3e039db48ef981bb9c26e3b652eeebaa), the [Modullar](https://app.notion.com/p/cea1e64dba26420d8a3d5088f9272201) database (one page per module, with its tasks), and the [competitor notes](https://app.notion.com/p/3e139db48ef981f2adb7f6d10f919ed5).

Starting a session on a new machine or after a break: read `docs/HANDOFF.md` first — current state, open issues, and setup.

## Commands

```
npm run dev          # vite dev server (http://localhost:3000 by default; pass --port to change); needs Postgres (DATABASE_URL, default postgres://localhost:5432/design)
npm run check        # service, database and feature tests (plain node scripts, no framework)
npx tsc --noEmit     # typecheck
npm run build:runtime  # build the screen runtime (React + Konsta + @od/kit + icons) into runtime/dist; check builds it if missing
npm run eval -- --label <name> [--vs <label>] [--only id,id] [--reshoot]   # eval/briefs.json through the real pipeline -> eval/out/<label>/
npm run judge -- <label> [--vs <label>|best] [--best]                      # vision judge (rubric + pairwise both orders) on a run's screenshots
```

A change is not done until `npm run check` and `npx tsc --noEmit` are clean. UI changes must also be exercised in a real browser (golden path plus one edge case) — type checks do not prove a feature works.

A change to generation (skill, kit, examples, planner, compiler) is judged on the eval set, not on one hand-picked prompt: `npm run eval -- --label <what-changed> --vs <previous>` (8 briefs on the real default model — GPT-6 Luna, about $0.10 a run — ~8 min; `--model <id>` runs every call site on another model; `LLM_PROVIDER=claude-cli` only for a free smoke run, since Haiku's results do not transfer) prints the metric deltas (build rate, crash rate, tokens and seconds per app, and source counts: Konsta parts, kit figures, emoji, palette colours, gradients, motion, nav calls, onboarding) and writes `index.html`, a contact sheet of every screen. Then `npm run judge -- <label> --vs <previous>` for taste. A kit fix is re-rendered over stored screens with `--reshoot` (no model calls).

## Model policy

**Which model runs is an admin setting per call site** (LLM-04/07): `llm.model.plan`, `llm.model.screen`, `llm.model.edit` and `llm.fallback`, read at call time (cached ~10s). Every model has an adapter (DeepSeek, Gemini and OpenAI through OpenAI-style Chat Completions — GPT-6 as a reasoning model: `max_completion_tokens`, no temperature, `reasoning_effort: none`; Anthropic through the Messages API, where a model that cannot switch thinking off, Opus 5.5, runs at effort `low` — `MODELS` beside `PRICES` in `LlmService`), a `PRICES` row and a `CREDIT_PRICES` row, which the credit price test holds to the model's own worst-case cost; a credit is charged at the model the action's site is set to. A 429 that says how long to wait is waited out and retried on the same model (twice at most; OpenAI's per-minute token limit). A call that fails before its first token is retried once on the fallback, or on the same model when no fallback is set (a dropped connection once left an app with no plan); nothing switches mid-stream; each attempt is logged under the model that ran. The default everywhere is GPT-6 Luna (`gpt-6-luna`, reasoning effort `none`; LLM-08, 2026-09-29: on the eval it beat DeepSeek V4.1 Flash 6–0–2 at about the same price, with −35% output tokens), and with no fallback set by the admin the fallback is DeepSeek V4.1 Flash, a second provider; `LLM_MODEL` changes the default (the tests pin `deepseek-flash`, whose shape their stubs answer in). DeepSeek V4.1 Flash is `deepseek-flash` (re-pointed from V4 to V4.1 on 2026-09-10 at the same price), not `deepseek-v4-pro` (`deepseek-flash`, which DeepSeek re-pointed from V4 to V4.1 on 2026-09-10 at the same price) — not `deepseek-v4-pro`. The id is pinned in `LlmService`, because `deepseek-flash` thinks by default and an alias can be re-pointed. (The old `deepseek-chat` id is an alias of exactly this configuration.) **Thinking is decided per call site, not once**: off for the six or seven screen calls, because reasoning tokens bill as output and output is the expensive half of an app (~47k of ~86k tokens; one plan measured 8 924 tokens / 89s with it on against 2 075 / 17s with it off), and off for the planner too, which an A/B settled rather than taste: on the same brief it produced a smaller plan for five times the output tokens and five times the wait (6 screens / 8.8s / 2 283 tokens against 5 / 43.6s / 10 658), and at the old 4 000-token cap the reasoning ate the JSON and two briefs drew nothing at all. `LLM_PLAN_THINKING=1` keeps the question askable — with it the planner's cap rises to 12 000, because reasoning spends the same budget as the answer. The price table (`PRICES`, by model, with `isPeak`) holds each provider's real list price and knows that DeepSeek's peak costs double, because the daily budget guard and credit prices spend against it; `costOf` refuses a model with no row instead of calling it free, and the process refuses to boot on a `DEEPSEEK_MODEL` it cannot price. Push correctness into deterministic code instead of asking a model to hold a contract — see the next section.

For local testing only, `LLM_PROVIDER=claude-cli` routes generation through the developer's own Claude Code login (`claude -p`) so trying things costs no DeepSeek balance. It runs on Haiku 4.5 by default — local testing is about seeing a change land, not about quality — and `CLAUDE_CLI_MODEL` overrides that when a run needs the bigger model. Thinking is off there as it is on DeepSeek (`MAX_THINKING_TOKENS=0` in the child's environment): with it on, one plan cost 8 900 output tokens and 89s instead of 2 100 and 17s, which reads as a hang. It refuses to run with `NODE_ENV=production`. Evals may run on it (`run.json` records the provider; a run is only compared with runs on the same provider) — such a result says how a code change moves quality, and key results are re-checked on DeepSeek before launch.

## Architecture rules

- **Screens are React JSX on Konsta UI v5 (iOS theme) + Tailwind v4 — there is no HTML pipeline** (KON-00, 2026-09-28; the old HTML engine is in git history). The model writes one screen as a default-exported component; `app/Services/ScreenCompiler.ts` parses it (@babel/parser), refuses any import outside `react`, `react/jsx-runtime`, `konsta/react`, `lucide-react`, `@od/kit` and any banned identifier (fetch, eval, storage…), transforms JSX with rolldown and builds the screen's own Tailwind CSS. Model code never runs in the server's own process; the one place it runs on the server is headless Chrome for the render check (KON-13, below), under a CSP with no network. A source that does not build gets one retry with the compiler's errors (`drawScreen` in `PlanController`), then the screen is a failed slot.
- **What the model gets wrong with Konsta is fixed or reported in code, not in the prompt** (HIG-10, `lib/jsx-lint.ts`, run in `drawScreen` before the compiler). A rule with one right answer is fixed in the source and the fixed source is what is saved: a `ListItem link` draws its own chevron (a second is removed), text on a `tint()` wash is never white, a `Block` pads itself (no `px-4` on it), a lone `bg-white` gets its dark pair, text is never under 11px (HIG Caption 2). A rule that needs a decision is reported — `ListItem`/`ListInput` outside a `List`, `BlockTitle` inside a `Block`, a `List` or `Card` inside a `Block`, more than two large buttons, an emoji in a control, a fixed bottom bar under the tab bar — logged as `[jsx-lint]` and counted by the eval (`hig`, `higByRule`). The compiler refuses a `<Tag>` nothing declares and the runtime does not have (it would crash the frame), so the screen gets its one retry; locals, destructured params and built-ins like `Number()` are not tags. A new failure mode gets a lint rule (fixed if it has one right answer) before it gets a prompt sentence.
- **A drawn screen is checked before anyone sees it, and repaired once** (KON-13 + HIG-15, `drawScreen`): after the lint and the compiler, `RenderAudit.auditScreen` opens it in headless Chrome (a private server on 127.0.0.1, a random token, CSP `connect-src 'none'`, images only from Pexels; `?static`, a phone wide and as tall as its content) and the kit measures it (`lib/render-audit.ts`, answered on `od:audit`): a box past the phone's edge, text cut off, text over text, text under a card, near-invisible text, half a phone empty. Those findings plus the lint's reported ones go into one rewrite; the rewrite is kept only if it builds and fewer problems are left. The chat log says `checked: N found, M left`. Measured on DeepSeek V4.1 (2026-09-29): most breakage was one Konsta trap the lint now fixes for free (a `BlockTitle` pulls up the next box by `-mb-2`; with no `Block`/`List` under it, or one whose margin the model changed, it gets `!mb-2`), so the paid rewrite is a safety net that rarely runs. The page is measured as iOS and again as Material, switched in place (HIG-16); an Android-only finding is named so. Without Chrome the check is the lint alone; `RENDER_AUDIT=0` turns it off (the tests do); the eval measures every final screen either way (`problemsPerScreen`, `cleanShare`).
- **Legibility and the type scale are the kit's job, not the model's** (HIG-12). Apple's text styles are Tailwind utilities (`text-large-title` … `text-caption2`, plus `text-figure` for a hero number; `runtime/type-scale.css`, read by both `runtime.css` and `ScreenCompiler`, and copied into an export). Text on a filled colour takes its colour from `onColor` (`runtime/kit/on-color.js`: white while white clears 3:1, otherwise ink), which `Hero`, a solid `Tile` and `gradient()`'s default second stop use — so a yellow or mint card never carries white text, whatever the model writes (the lint drops `text-white` on a `Hero`). Kit code stays plain and self-contained under `runtime/kit/`, because the export copies that folder. The eval counts `adHocText` (`text-[Npx]`) against `namedText`.
- **The model learns Konsta from files, not from memory**: system prompt = `skills/mobile-screen-jsx/SKILL.md` (HIG-first, ≤8k characters: structure, one primary action, inset grouped lists, text styles, then colour, emoji and photos) + `konsta/KIT.md` + `konsta/USAGE.md` (HIG-13: right/wrong JSX for the mistakes the lint keeps seeing) + `konsta/REFERENCE.md` (generated by `scripts/konsta-reference.mjs`), and every screen brief carries one finished screen from `konsta/examples/` chosen by its kind (`exampleFor`: first-run → onboarding, the first tab → dashboard, other tabs → list, pushed/modal → detail). An example is the strongest lever on quality — it is copied for its build, never its data or palette. Prompts and planner live in `app/Services/JsxGenerator.ts`.
- **The bar is a top App Store app, not restraint** (2026-09-28): the skill asks for colour with confidence (gradient hero tiles, tinted tiles, coloured figures), emoji as content (item icons, awards, onboarding art — never in buttons, navbars or body text), motion (`vs-rise` stagger, `vs-float`, `CountUp`, `Confetti`) and a first-run onboarding for consumer apps. Measured on the eval: colours 1.7 → 6.3 per screen, emoji 0.6 → 4.2, onboarding 2 → 8 of 8 apps, at +50% output tokens and +43% time per app.
- **An app has one of five styles, and its colours are the code's** (THM-01, researched on 47 top iOS apps: Clean ~30%, Midnight ~25%, Vivid, Soft, Editorial ~15% each). The planner picks `style` from the five (by what the audience would expect) and names 3–6 palette keys; `parsePlan` with the project id as seed takes the palette colours from that style's own set, starting where the seed says (`styleColors` in `lib/app-theme.ts`, FNV-1a with a murmur finaliser — plain FNV's low bits gave two eval apps the same colours), and the accent is the first of them that darkens to white-text contrast in a few steps (an accent picked apart from the palette clashed with it) — the model never writes a hex, because shown eight iOS hues it put every app in the same eight. Every accent reads as a button with white text (≥3.5:1, tested). `appContext` gives every screen the style's card (`STYLE_CARDS`: how to compose, including onboarding) and the same `const C = {…}` line. A midnight app starts dark.
- **A style is CSS variables, so switching it recolours every screen in place** (`runtime/kit/styles.js`, `applyStyle` in `mount` after the accent, also in the export): it sets Konsta's own surfaces (iOS `--color-ios-*-surface*`, Material `--k-color-md-*-surface*`), the kit's `--app-page/card/card-2/line/radius` behind the Tailwind utilities `bg-page`, `bg-card`, `bg-card-2`, `border-line`, `rounded-card` (in `runtime/type-scale.css`'s `@theme`, read by the compiler and the export), and the fonts (`data-app-font` / `data-app-display`: rounded for Vivid and Soft, a serif for Editorial's titles). A screen's own boxes use those classes; the lint turns `bg-white` (and its hard-coded dark pair) into `bg-card`. Every style's page and cards keep ≥7:1 with the label colour, light and dark (tested). The Style & colour panel shows the five with a preview.
- **What the compiler can repair with one right answer, it repairs**: a Konsta component, kit export or lucide icon used but never imported is imported for it (a forgotten `BlockTitle` import crashed a screen). A screen that still throws shows "This screen crashed: …" (kit `Crash` boundary, and a catch around the module load) instead of a blank frame; the eval counts these as `crashRate`.
- **The plan is a contract checked in code** (`parsePlan`; HIG-17: screens the brief names are `asked` and survive the eight-screen cut — unasked pushed screens go first, then an unasked tab; `data` gives every fact one value app-wide; the planner is told today's date): 3–5 tabs with icons from `TAB_ICONS`, screens of kind `tab|push|modal|first-run`, one root screen per tab, tabs no screen opens pruned, a push with no parent goes back to the first tab, an accent that is not `#rrggbb` falls back. The plan is stored in `projects.plan`, tabs in `projects.navigation`, the accent in `projects.theme`; its `data` block rides every screen brief, so screens share names and numbers.
- **The source is stored as it was written** (`screens.html` holds the JSX; `isJsx` tells old HTML rows apart, which are served raw). `screens.slug` is the plan id that `useNav().push(slug)` and `reset(tabId)` address.
- **A screen runs on a prebuilt runtime** (`runtime/`, `npm run build:runtime` → `runtime/dist`, gitignored): React, Konsta, `@od/kit` (Ring, Rings, Bars, Area, Heatmap, Meter, WaterGlass, CountUp, Tile, Medal, Avatar, Glow, Dots, Confetti, `tint`, `gradient`, AppTabbar, useNav, `mount`; `?static` adds `vs-static` so screenshots show finished screens) and one module per lucide icon, served by `/api/rt/v<build>/…` with CORS `*`. The build segment is the runtime's mtime, so a rebuilt kit is a new URL under the hour-long cache. A kit prop that takes a colour accepts only a CSS colour (`cssColor`); a Tailwind class there becomes the accent.
- **A screen's page is `/api/thumb/$screenId`** (`ScreenDocument`): import map + runtime CSS + the screen's CSS + its compiled code inlined as a blob module (a sandboxed page fetching it from us would go without cookies). Owner or admin only, CSP `sandbox allow-scripts`; `?dark=1`, `?v=<versionId>`, `?static`. The canvas, preview and dashboard frame it with `sandbox="allow-scripts"`; `ScreenFrame` adds `r=<hash of source>` so a changed screen is a new URL.
- **Photos are real and looked up at save** (KON-12, `PhotoService`): the model writes `<Photo q="what it shows">` (kit) and gives data items a `photo` query; `photoQueries` reads them from the source (literals and `photo`-like keys, never executed), `resolvePhotos` runs in `drawScreen` and fills `image_cache` from Pexels (key via `SecretService`, only `images.pexels.com`, a miss is cached too), and `ScreenDocument` passes the cached URLs to `mount` — a render never calls Pexels, the model's code is never rewritten, and a query without a photo is a tinted block. Pexels allows 200 lookups an hour, so queries are normalised and shared through APP DATA; the eval keeps its lookups in `eval/photo-cache.json`. The preview no longer shows a Pexels credit (the owner's call, 2026-09-28); Pexels' API guideline asks for a visible link, so one belongs somewhere else in the product.
- **A frame is as long as its screen** on the canvas: the kit's `mount` reports the `.k-page` scroll height (`od:height`), `ScreenFrame` grows the frame (each version measured from a phone-tall viewport, so an edit can shrink it) and the canvas saves it to `screens.height` (clamped 844–5000) to lay out the next load. The preview stays one phone tall and scrolls.
- **The app's look is the app's, not the studio's** (KON-11, `lib/app-theme.ts`): `projects.theme` holds `{ accent, dark, platform: 'ios' | 'material', style }`, set from the canvas: platform (iOS | Android) and light/dark are a pill in the top bar (`AppLookSwitch`) because they are flipped all the time and their current value must show; the accent is the Colour panel on the rail (`ThemePanel`). Debounced save, one undo step per burst. The preview has the same switch, view-only. The same JSX renders natively for both platforms: `mount` sets Konsta's `App theme`, and derives Konsta's colour tokens (`--k-color-*`) from the accent with Konsta's own colour math — iOS tint/shade always, the Material You scheme (`md-colors`, a 21 KB chunk) only for Android. The look is not in a frame's URL: the frame posts it into the running page (`postLook` → `od:look`, validated in the kit, only from the parent) and `mount` re-renders in place — a URL change reloaded every frame on each switch, which lagged. A page first draws with the stored theme; the thumb route still accepts `a`/`p`/`dark` (`themeFromQuery`) for links. The studio's own light/dark never reaches a screen.
- **A frame that is being drawn or is still loading sits under a deep blur that resolves when it is ready** (`GeneratingVeil`, macOS Image Playground style): three blur layers (40px, 14px, 4px) fade out deepest first over ~1.4 s, so the screen goes deep → light → sharp; no sheen or label. Opacity only (animating `backdrop-filter` itself is too heavy for eight frames at once), inside `prefers-reduced-motion: no-preference`.
- **Undo and redo run one at a time** (`UndoStack` queues them): two quick ⌘Z presses used to run both steps at once, and the slower save won.
- **Export is a headline feature and is shown as one** (a labelled primary Export button in the top bar, formats in its menu). **CODE-01: the app exports as a React + Vite project** (`ExportService.exportReact`, `GET /api/export/$projectId`, owner or admin, a plan without export gets 402 → the upgrade dialog): the screens are the stored JSX with the imports they forgot (`completeImports`, the same function the compiler builds from) and the kit's `ListItem` (`withKitListItem`), plus the kit (`runtime/kit`), a stack navigator (`runtime/export/main.jsx`; the kit's `useNav` takes a navigator from context, else posts to the host), `app.json` (screens, tabs, theme), `photos.json` and Konsta's stylesheet with the accent as `--color-brand-primary`. On a wide screen it sits in a phone frame. `npm run check` builds an export with Vite; a change to the kit, the navigator or the export must keep that green.
- **CODE-02: one HTML file** (`exportHtml`, `?format=html`): the CODE-01 project built by Vite on the server with the script and stylesheet inlined — it opens from a file with nothing beside it; served as an attachment with a CSP sandbox. Vite and its plugins are production dependencies for this. **CODE-03: View code** shows a screen's code exactly as the export ships it (`ScreenController.code`).
- **FIG-10/11: Copy to Figma** is the kit's own serializer (`lib/figma-serialize.ts`, answered by `mount` on `od:serialize`, only from the parent): the laid-out DOM as a tree of layers named from Konsta's classes and the kit's marks (`data-od-photo`, `data-od-kit`), the Konsta page read at full height; `lib/figma-svg.ts` writes it as one SVG (photos embedded as data URLs) that Figma turns into editable, named layers on ⌘V. From a frame, the selection or the whole app, placed as on the canvas. `eval/figma.check.ts` measures it in headless Chrome on an eval run (every screen serialises, has text, keeps its photos).
- **A frame asks until it hears** (`od:measure`): a height report sent before the frame listened would leave it under its veil, so an unmeasured frame asks once a second. `runtimeExports` and the runtime URL follow a rebuild of the runtime (by `exports.json`'s mtime) instead of failing mid-build or needing a restart.
- **Navigation is a message** (`od:nav` push/pop/reset from the kit's `useNav`), validated by `parseNav` and resolved by `screenForNav` (slug, else the tab's root screen). The preview keeps one iframe per screen and only switches which is shown; on the canvas a tap focuses the target screen. A frame only trusts messages whose `e.source` is its own iframe.
- **The canvas is simple**: screens, chat and composer. A message with nothing on the canvas plans the app; with screens selected it edits each (the model gets the component and the change); otherwise it adds a screen that joins the plan. No element editing, theme panel, export, Figma or code view.
- **The conversation is written by the controllers, in code** (`messages`, `lib/agent-messages.ts`): each agent message points at the snapshot taken before its change, which is what makes "Undo this step" exact; ‹ › steps a screen's versions.
- **Every canvas action is undoable from the keyboard** (`lib/undo-stack.ts`): an action records its inverse (`pairStep`) or writes a conversation message (`messageStep`).
- **A deleted screen keeps its row** (`deleted_at`); a failed one keeps its slot (`html = ''`, `error`, `spec`) and can be retried in place. Listings skip empty `html`.
- **The database is Postgres** (INF-10; `database/connection.ts`, `DATABASE_URL`). Every model method is async. Times the app writes are unix seconds, Better Auth's are `timestamptz`. A migration is a numbered file in `database/migrations`, registered in `database/migrate.ts`. Tests use `DB_FRESH=1` (a throwaway database per process) and `scripts/alias-hook.mjs` to resolve `@/` in plain node.
- **Layers:** `app/Models` (data access), `app/Services` (logic), `app/Http/Controllers` (request handling), `routes/` (TanStack file routes), `server/fns.ts` (route-to-controller binding).
- **The compiler's packages stay out of Vite** (`SERVER_ONLY` in `vite.config.ts`: native binaries).
- **The studio has one warm palette, in `src/styles.css`** (UI-01): a single sand ramp that light and dark both take their surfaces from, and a brand colour used on a handful of controls — never as a surface, because the screens on the canvas are the colourful thing. No chrome value is a chroma-zero grey or pure black, and a test in `new-features.check.ts` keeps it that way. A screen on the canvas is drawn without a card around it (`--canvas`/`--canvas-dot` are the canvas's own tokens), and the Theme panel can show a colour without saving it (`onPreview` → `themePreview`, which the frames render instead of the saved theme).
- **The brand is warm ink and electric lime, and lime is only ever a fill** (UI-10): `--primary` is lime with ink on it; lime is never text and never the focus ring (`--ring` is ink, 3:1 on every surface), and `new-features.check.ts` checks both contrasts. Tokens are OKLCH in `src/styles.css`, with one type scale (12…64, `text-md` is 13px), four radii plus `--radius-phone`, `--elevation-1…4` and spring/ease-out motion that reduced-motion turns off. Type is self-hosted Instrument Sans with Instrument Serif italic for accents — no Google Fonts request from the studio. A phone bezel is `components/PhoneFrame.tsx` and a prompt box is `PromptBox` (`variant="hero"` on the landing): one of each, never a local copy. A screen that is waiting or streaming shows a phone-shaped shimmer from the studio's tokens laid over its slot until first content (UI-13) — an overlay beside the iframe, never something written into it.
- **The canvas is the whole window and everything else floats over it** (UI-20…24, Stitch's layout): the top bar is two pills (☰ project menu + name | Preview, Share, account); the chat is a folding card at the left (`ChatDock`); the composer sits at the bottom centre of the free canvas with the selection as chips inside it (`PromptBox variant="dock"`, `top`); tools are a rail at the right (`Canvas` `rail`), history and zoom at the bottom right. `Canvas` takes `insets` — what the floating panels cover — so fit and focus centre in the free area; a new floating panel updates `canvasInsets`. A selected frame's actions are a bar at screen size above it (`FrameToolbar`, `FrameLabel free`), never scaled with the frame; 
- **Things on the canvas arrive and leave, they do not blink** (UI-25): motion is a small vocabulary in `src/styles.css` (`od-rise`, `od-fade`, `od-land`, `od-pop`, `od-slide` with `data-open`, `od-glide`) — transform and opacity only, on the `--duration-*` / `--motion-ease-*` tokens, all inside `prefers-reduced-motion: no-preference` (a test holds it). A new panel or popover uses one of these classes instead of its own keyframes; a panel that slides stays mounted and is `inert` when closed; programmatic view moves call `glide()`, wheel and drag never do.
- **The preview shows the app on a device we draw ourselves** (PRV-01, `lib/devices.ts`, `components/DeviceFrame.tsx`): each device has its CSS viewport and safe areas. The screen is laid out at that width, and the insets reach the kit through `od:look`, which sets `--k-safe-area-*`, so Konsta's bars keep clear of the status bar and home indicator. An Android phone switches the look to Material. No vendor artwork (Apple's 3D assets are not licensed for this). A new device is one row in `DEVICES`. A foldable (`unfolded`, PRV-02) opens to two panes decided in code from the plan (`splitPanes`: a list left of what it opens, anything else full width); both panes may navigate. The Duo is commented out of `DEVICES` until November 2026; its geometry (`foldLayout`) and tests stay. The preview stage is a presentation (PRV-03): no grid, a light in the app's accent behind the phone, and every control carries `od-chrome`, so it fades after 2 s idle and wakes on any move — a new preview control gets the class too.
- **A preview is private until its owner shares it** (SHR-02, `ShareController`): Share → Public link sets `projects.share_token` (16 random bytes); off drops it, so the old link dies. `/s/$token` is public and view only — the same stage as the owner's preview (`components/AppPreview.tsx`), no way into the editor — and its frames carry `?t=<token>`, which `/api/thumb` accepts for a shared project's current screens only (never `?v=`). A stranger's loader gets no owner, project id, messages or source (a screen's `html` there is a hash, the frame's version key), because the source is what the paid export sells. Under 640px the preview draws no device: the app is the page (SHR-05). A shared page offers the waitlist (WLT-01, `waitlist`, one row per email); each open is a `share_views` row, and `?ref=` names the post it came from, so the admin dashboard shows views and sign-ups per post.
- **Every public page wears the same chrome** (UI-15, `components/SiteChrome.tsx`): `SitePage` (or `SiteHeader`/`SiteFooter` on the landing) with the one `BrandMark`, the nav, the theme toggle and a lime "Start free"; headings use `Em` for the one serif word. A missing route, a loader's `notFound()` and an uncaught error render `components/NotFound.tsx` (the router's defaults), never the framework's bare text. A new public page goes inside `SitePage`.
- **The admin draws on the studio's tokens only** (UI-18/19): tables, filters, pagers, callouts, segmented controls and status pills come from `src/admin/ui.tsx` (`tbl`, `control`, `Pager`, `Callout`, `Segmented`, `Badge`); status colour is `--success`/`--warning`/`--destructive` (each 4.5:1 on background and card, tested); charts take `--chart-*`. A test in `new-features.check.ts` rejects Tailwind palette colours, hex, 10/11px text and default shadows anywhere in the admin.

- **The admin reads large logs one page at a time** (ADM-11): `ServerTable` (`src/admin/ui.tsx`) keeps search, filters, sort and page in the URL, and the server does WHERE/ORDER/LIMIT (`AdminStatsService.*Page`). Every sort column and filter value is whitelisted in `src/admin/table-query.ts` (unknown → default, never an error), ILIKE text is escaped, CSV follows the same filter (capped at 10 000 rows, formula-leading cells quoted). The old in-memory `DataTable` is for small lists only.
- **Telescope records every request and every server log line** (OBS-10/11): `src/start.ts` is the global request middleware — a request id in `RequestContext`, then method/path/status/ms/user (`http_requests`); console output and uncaught errors land in `server_logs` with that id and an error `fingerprint` for grouping; LLM calls carry `request_id`. It never stores bodies, cookies, Authorization headers or raw IPs (a truncated hash), masks secret-looking query params and `Bearer` tokens in log text, skips static/dev assets, and keeps 7 days (200 000 rows at most). Recording is fire-and-forget and must never delay or fail a response. Defining `requestMiddleware` drops TanStack's default CSRF check for server functions, so `start.ts` puts it back after the recorder — keep it there.
- **Telescope also records what the server calls out and what calls in** (OBS-12): the server's `fetch` is wrapped once (installed from `start.ts`, server-only) and every non-local call is kept in `outgoing_requests` — host, path with secret params masked, status or network error, ms, purpose, request id — never bodies or headers, and the response is returned untouched. Every POST to a webhook route lands in `webhook_events` (payload only when the signature verified); an admin may replay a stored verified event through the same handler, which the ledger's refs make harmless.
- **The admin opens on money** (ADM-20, `DashboardService`, `routes/admin.index.tsx`): Sold (the `orders` table, in dollars), LLM spend (`llm_calls.cost_usd`) and Profit (sold − fees ≈ 4% + $0.40 an order − LLM), large, against the window before; then tokens with their dollars — input, cached input and output per model, split at each model's list rates and scaled to what was really charged, so the parts add up — cost per app and per screen, today against the budget; a 30-day sold/spend chart; and only signups, active users, apps and MRR. The sidebar puts Business (Dashboard, Users, Credits & revenue), AI (Generations, Models) and Settings first; the Telescope pages (Errors, Requests, Logs, Outgoing, Webhooks) sit folded under Debug. The old ledger-based revenue estimate (`OverviewService.windowStats`) is gone; `OverviewService` keeps MRR and the alerts.
- **Revenue is a fact, not an estimate** (ADM-15): each `order.paid` is stored once in `orders` (id = the provider's order id), and the credits page, per-user margin and the overview read it. The overview's MRR comes from live subscriptions at their monthly-equivalent price (ADM-12).
- **A model that is down is routed around** (ADM-14): with ≥5 calls in 15 minutes and ≥50% failed, a site whose primary is that model runs on its fallback for 5 minutes (if one is set and healthy), then tries the primary again; the decision is logged. Health is computed from `llm_calls` and injected into `LlmService` (which stays free of the database).

## Accounts and limits

- **Server functions and API routes check the caller; controllers trust theirs.** Every function in `server/fns.ts` runs `requireUser` / `requireProject` / `requireScreen` (`server/auth.ts`) and validates its input with `server/validate.ts` before calling a controller; the streaming routes go through `server/guard.ts` (sign-in, ownership, same origin, limits). A new server function does the same, or it is an open door. Controllers stay callable directly for the eval and the tests.
- **Stored screen HTML is never served as a page of our origin.** Dashboard thumbnails come from `/api/thumb/$screenId` (owner only, 404 otherwise) with `Content-Security-Policy: sandbox allow-scripts` and are framed with `sandbox="allow-scripts"`; any new route that returns generated HTML does the same.
- **The admin panel checks on the server, every call.** `/admin/*` routes and every function in `server/admin-fns.ts` go through `requireAdmin()` (a non-admin gets the same 404 as a missing page); an admin is `user.role = 'admin'` or an email in `ADMIN_EMAILS`. Every admin write goes through `AdminController`, which logs it in `admin_actions`. Runtime switches (pause, limits, budget, per-user limits) live in `settings` and are read through `UsageService.limits()` — an env `GENERATION_PAUSED=1` still wins. A banned user counts as signed out in `userFrom`.
- **A planned run outlives its page** (`PlanRuns`): closing or reloading the tab stops the events, not the drawing; only Stop (`/api/stop-plan`) ends it, and `guardGeneration` releases the one-at-a-time lock when the run finishes (`X-OD-Detached` + `finish`). A single-screen edit still stops with its page.
- **Credits are a ledger, never a number on the user** (`credit_ledger`, `app/Models/Credit.ts`, BIL-04): every grant, hold, refund and purchase is a row with a whole `delta`, and a balance is the sum. A row caused by something outside an action (a payment event, a signup) carries a `ref`, which is unique, so a webhook delivered twice grants once. An admin changes a balance only by adding a row (`grantCredits`, logged in `admin_actions`) — never by editing one.
- **An action pays before it runs, and only for what it delivered** (BIL-06, `CreditService`, `server/guard.ts`). `guardGeneration` prices the request (`kindOf` + `CREDIT_PRICES`, by model) and holds the price before any model is called — a short balance is a 402 with `{ error: 'credits', needed, balance }`, and nothing is written. When the action ends, `settle` gives everything back if none of its model calls succeeded; a planned run pays back each screen it did not draw (failed or stopped) at a screen's price. A refund never exceeds what the action still holds, so settling twice is harmless. A new generation route goes through `guardGeneration` or it is free.
- **Money arrives only through a verified webhook** (BIL-09/10/11, Polar — Stripe does not open accounts in Uzbekistan). Checkout and the billing portal are the provider's hosted pages (`PolarService`), tied to our user by `external_customer_id`; products are found by `metadata.od` (`PRODUCTS` in `lib/credit-prices.ts`, created by `scripts/polar-products.ts`), never by pasted ids. `/api/polar-webhook` believes nothing before its Standard Webhooks signature (`lib/standard-webhooks.ts`, five-minute window). A pack is granted on `order.paid` with ref `order:<id>`; a plan is a `subscriptions` row that every subscription event rewrites, and its credits are granted per month of the plan (`CreditService.refresh`, ref `sub:<id>:<month>:<product>`, yearly plans monthly too) — before each new month, what is left of the last plan grant lapses; packs never lapse. `refresh` runs wherever a balance matters (the guard, `getCredits`, webhooks), so a renewal needs no scheduler.
- **A plan's limits are code, not copy** (BIL-14, `PLAN_LIMITS` in `lib/credit-prices.ts`, `CreditService.limitsFor`): Free 1 project, Starter 5, Pro unlimited, and export (zip, HTML, Figma) on paid plans only; an admin is not limited. The project count is refused on the server in `ProjectController.store` (every way a project is made passes it); export is held in the page (`mayExport`), because the screens are already in the browser — a plan limit, not a lock. /pricing lists only what the code keeps.
- **Prices are data shared by server and browser** (`lib/credit-prices.ts`: `CREDIT_PRICES`, `PLANS`, `SIGNUP_CREDITS`). The browser never computes a charge; it shows the balance (`CreditsBadge`, the dashboard card) and reloads it when any generation ends (`creditsChanged` in `generate.ts` / `generatePlan.ts`). A 402 from a guarded route becomes `OutOfCredits` (`failFrom`) and opens the one `CreditsDialog` mounted in the root — never a toast (`reportError` stays silent for it).
- **A stranger gets 404, never 403** for someone else's project — its existence is not confirmed.
- **Every model call is logged** (`llm_calls`, via `LlmService.onLlmCall` + `UsageService`), attributed to the request's user, project and action through `AsyncLocalStorage`, with the model that answered and its cost from that model's own price. One guarded request is one action (`action_id`, minted in `guardGeneration`); `UsageService.actionCost` is what the action really cost, which is what a credit is measured against. The limits (`UsageService.refusal`: calls per user per day, one generation at a time, daily budget, `GENERATION_PAUSED`) read that table. A new generation path must run inside `guardGeneration` or it escapes both.
- **Provider keys are entered in the admin panel** (ADM-13, Settings → API keys; `SecretService`): DeepSeek, Gemini, Anthropic, Pexels, Polar token and webhook secret. A key saved there wins over `.env` and is stored sealed (AES-256-GCM, `app/Services/secret-box.ts`) with the master key `SECRETS_KEY`, which lives only in the environment — the database alone reads nothing, and losing `SECRETS_KEY` means re-entering the keys. The browser only ever receives a key's last four; the admin log records the last four; "Test connection" returns an outcome, never a provider's body. Code reads a key through `SecretService.get` (LlmService through `setKeySource`, so its plain-node tests need no database) — never `process.env` for a provider key.
- Secrets that stay in `.env` only: `SECRETS_KEY`, `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GOOGLE_CLIENT_ID/SECRET`. The magic link is logged to the console in development and refused in production until an email provider exists (EML-01).

## Git

- Commit and push only when the user asks.
- Pushing over HTTPS needs the GitHub CLI credential helper:
  `git -c credential.helper='!gh auth git-credential' push origin <branch>`
- Never commit `.env` or `data.db*` (both are ignored). `data.db` is the pre-Postgres SQLite file, kept as a backup; `scripts/sqlite-to-pg.ts` copies one into an empty Postgres.
